# Part A — Security & Compliance Plan (Security Lead)

## A1. Security objectives

1. **Customers' cloud accounts are never put at risk by us:** read-only access, no long-lived keys, no confused-deputy path.
2. **No cross-tenant data exposure**, ever.
3. **Trust that passes vendor reviews** at African fintechs, banks and their auditors (and UK/EU customers).
4. **Proportionate controls** for a small team: automate evidence and build SOC 2 / ISO 27001 controls in from the MVP.

## A2. Assets & trust boundaries

| Asset | Sensitivity | Where |
|---|---|---|
| Access path into customer AWS accounts (broker role, Roles Anywhere CA, ExternalIds) | **Critical** | Our AWS broker account; secrets manager; DB (encrypted) |
| Customer billing data, resource inventory, tags, metrics | High (commercially sensitive; tags may contain personal data) | Spaces, PostgreSQL |
| User accounts, sessions, MFA secrets | High | Auth provider, DB |
| Integration tokens (Slack, later Jira/Git) | High | DB (envelope-encrypted) |
| Recommendations/outcome data (M2 dataset) | Medium–High | DB |
| Source code, CI/CD, container images | High (supply chain) | GitHub, registry |
| Audit logs | High (integrity) | DB + archive |

**Trust boundaries:**
1. User browser ↔ CDN/API.
2. API ↔ data stores.
3. Workers ↔ our AWS broker account (Roles Anywhere).
4. Broker ↔ customer AWS accounts.
5. Platform ↔ third-party SaaS (email, Slack, FX, analytics).
6. Staff ↔ production (break-glass).
7. CI/CD ↔ production.

## A3. Threat model (key risks & mitigations)

Method: STRIDE per trust boundary. The domains follow the attack classes of the Cloudflare `security-audit` skill referenced in `extra.md` (tenant isolation, cloud IAM, supply chain, data lifecycle, resource exhaustion, AI/LLM, client-side).

| # | Threat | Boundary / STRIDE | Likelihood | Impact | Mitigations | Residual |
|---|---|---|---|---|---|---|
| T1 | **Confused deputy:** attacker tricks Cloudoptics into reading another company's AWS account (supplies a victim role ARN) | 4 / Spoofing | Med | **Critical** | Unique, unguessable ExternalId per connection generated by us (never user-chosen); one AWS account ID per workspace (`UNIQUE`); trust policy pins our broker role ARN; validation checks the role's trust policy contains our ExternalId | Low |
| T2 | **Compromise of our Roles Anywhere CA or broker role** → access to all customers' read-only data | 3–4 / Elevation | Low | **Critical** | CA key in a managed/HSM-backed store (AWS Private CA short-lived mode, or Vault PKI with offline root); certs ≤ 24h per pod; broker role can only `sts:AssumeRole` into `CloudopticsReadOnlyRole*`; SCPs on the broker account; CloudTrail + alerts on trust-anchor/role/policy changes; optional customer `aws:SourceIp` pinning to our static egress IPs; break-glass procedure to revoke the trust anchor | Low–Med |
| T3 | **Cross-tenant data leak** (missing tenant filter, cache-key collision, export of other tenants' rows, signed URL reuse) | 2 / Information disclosure | Med | **Critical** | PostgreSQL RLS on all tenant tables; tenant-scoped query builder for DuckDB/Parquet paths; cache keys namespaced by tenant; exports re-authorised per item; signed URLs bound to object + 15-min expiry; automated cross-tenant tests in CI; 404 (not 403) for foreign IDs | Low |
| T4 | **Stored XSS / injection via customer-controlled strings** (tag values, resource names, account names arrive from AWS and are shown in UI, PDFs and Slack) | 1 / Tampering | **High** | High | Treat all cloud metadata as untrusted; framework auto-escaping; strict CSP (no inline scripts); sanitise for Slack mrkdwn and PDF rendering; **CSV formula-injection guard** (prefix `=,+,-,@` cells) in exports | Low |
| T5 | **Account takeover** (credential stuffing, phishing, session theft) | 1 / Spoofing | Med | High | MFA (TOTP; tenant-enforceable); breached-password check; rate limits and lockout; secure cookies (httpOnly, Secure, SameSite) + CSRF tokens; session revocation on password/role change; new-device login emails; SSO (SAML/OIDC) in v1 | Low–Med |
| T6 | **Broken access control / privilege escalation** (Viewer changes settings; removed user keeps access) | 1–2 / Elevation | Med | High | Server-side RBAC on every endpoint (`x-required-role` tested); membership checks per request (no long-lived role caching); session/token invalidation on removal or role downgrade | Low |
| T7 | **Secrets exposure** (keys in logs, images, CI, error reports) | 2, 7 / Info disclosure | Med | High | Secrets only in the secrets manager; log redaction middleware; secret scanning (pre-commit + CI + GitHub push protection); no secrets in env dumps or crash reports; rotation runbooks | Low |
| T8 | **Supply-chain compromise** (malicious dependency, compromised CI action, tampered image) | 7 / Tampering | Med | High | Pinned dependencies with lockfiles; Dependabot/Renovate; SCA scanning; GitHub Actions pinned to commit SHAs with least-privilege `GITHUB_TOKEN`; OIDC from CI to cloud (no static deploy keys); image signing (cosign) + admission verification; SBOM per release | Low–Med |
| T9 | **Resource exhaustion & spend abuse** (expensive queries, export floods, job storms; customer-side AWS API charges run up) | 1–4 / DoS | Med | Med | Rate limits per user/tenant; query timeouts and row limits; async exports with quotas; per-tenant job concurrency; **per-tenant AWS API spend budget** with circuit breaker; WAF/bot protection | Low |
| T10 | **SSRF / outbound abuse** via user-supplied URLs (webhooks, logo upload by URL) | 5 / Elevation | Low–Med | Med | Allow-list schemes; resolve-and-block private/link-local ranges; egress proxy for user-supplied destinations; no fetching of metadata endpoints; signed webhooks | Low |
| T11 | **Insider / staff misuse** | 6 / Info disclosure | Low | High | Least-privilege staff roles; production access via SSO + MFA + just-in-time elevation; break-glass with reason, time limit and tenant-visible audit entry; quarterly access reviews; background checks per local law | Low |
| T12 | **Audit log tampering / repudiation** | 2 / Repudiation | Low | Med | Append-only grants; hash-chained rows; monthly export to write-once storage; time sync | Low |
| T13 | **Backup / replica exposure** (wider access, missed deletions) | 2 / Info disclosure | Low | High | Encrypted backups; restricted restore roles; secondary-region replication under the same controls; deletion propagation documented (backups age out ≤ 30 days); restore re-applies deletion tombstones | Low |
| T14 | **Email / brand spoofing** (phishing users with fake "Cloudoptics alerts") | 5 / Spoofing | Med | Med | SPF/DKIM/DMARC `p=reject`; consistent alert templates; never ask for credentials by email; in-app notification mirror | Low–Med |
| T15 | **(v1) LLM assistant prompt injection** via tags/resource names or user prompts → data disclosure across tenants or harmful instructions | 1–2 / Info disclosure | Med | High | Assistant tools scoped to the session's tenant; retrieval enforces tenant filters server-side; no write tools; treat cloud metadata as data, not instructions; output encoding; red-team before launch (Cloudflare skill `AI-AND-LLM` classes) | Low–Med |
| T16 | **Unsafe guided fix** causes a customer outage (reputational/legal) | Product | Med | High | Risk scoring, pre-steps and rollback; templates tested in CI and in a test AWS account (incl. `af-south-1`); clear "review before applying" disclaimers; ToS liability limits (counsel) | Low–Med |

## A4. Authentication & authorisation design

| Area | MVP | v1 | v2+ |
|---|---|---|---|
| **Login** | Email/password (≥ 12 chars, breached-password check), Google OIDC | SAML/OIDC SSO (Google Workspace, Microsoft Entra ID, Okta) | SCIM provisioning |
| **MFA** | TOTP; tenant can require it; recovery codes | WebAuthn/passkeys; SSO-enforced MFA | Step-up MFA for sensitive actions (e.g., enabling write role) |
| **Sessions** | httpOnly Secure SameSite cookies; idle 12h / absolute 7d; revocation | Device/session management UI | — |
| **RBAC** | Admin / Member / Viewer per tenant | Account-scoped roles (e.g., Member for accounts A, B); Finance role | Custom roles; partner delegated admin |
| **API access** | Session only | Personal access tokens / API keys (scoped, expiring, hashed) | OAuth2 client credentials (partners) |
| **Staff access** | Break-glass tool, JIT, audited | — | — |
| **Write role (future)** | — | Separate opt-in `CloudopticsActionRole` with per-action permissions, dual approval option, step-up MFA, change windows | Policy automation guardrails |

## A5. Data protection (encryption & key management)

| Layer | Control |
|---|---|
| In transit | TLS 1.2+ everywhere (1.3 preferred); HSTS preload; TLS to PostgreSQL/Valkey/Spaces; mTLS not required inside the cluster for MVP (network policies), reconsider at v2 |
| At rest | DO-managed encryption for DB, volumes, Spaces and backups |
| Application-level | **Envelope encryption** for ExternalIds, integration tokens, webhook secrets and MFA seeds (if stored by us): data keys encrypted by a KMS key (Vault Transit or a cloud KMS), with rotation yearly and on incident |
| Key management | Separate keys per environment; KMS access only for the app service identity; key usage logged; documented rotation and revocation |
| Data minimisation | Only billing, metadata, metrics and tags; no application data, no payment-transaction data; tags flagged as potentially personal |
| Deletion | Tenant/connection deletion within 30 days, incl. object storage and derived data; certificate of deletion |

## A6. Audit logging & traceability

- **Tenant-visible audit log (product):** logins, MFA changes, user/role changes, connection create/validate/disconnect, settings, budgets, recommendation status changes, exports, data deletion, staff break-glass access. Retained ≥ 12 months online, 3 years archived.
- **Platform security logs:** auth provider events, admin/console access to DO and AWS (CloudTrail in the broker account, all regions), Kubernetes API audit logs, CI/CD deploy logs. Centralised in the logging platform, kept 1 year.
- **Traceability:**
  - Every request and job carries `request_id`/`job_id` and `tenant_id`, linked to traces.
  - Recommendations carry `engine_version` and input references.
  - Deployments are tagged with commit SHA and SBOM.
- **Alerting (security):** CloudTrail changes to the broker account/trust anchor; unusual assume-role volume; spikes in failed logins; MFA disabled by an admin; staff break-glass use; audit-chain verification failure.

## A7. Compliance considerations

### A7.1 Roles under data protection law
- **Processor** for customer billing/resource data (processing on customers' instructions under a DPA).
- **Controller** for our own user account data, product analytics and marketing.

### A7.2 Regulations by market

### A7.4 Data residency

- **Current position:** all customer data is stored and processed in the **UK (DO LON1)**, with encrypted backups in the EU (AMS3/FRA1). **DigitalOcean has no African region.**
- **Messaging for African customers (security pack):**
  - What we store (billing and metadata only, not application or payment data).
  - Where we store it, the legal transfer basis per country (NDPA, Kenya DPA, POPIA clauses) and our sub-processors.
  - How customers can delete their data.
- **Future option (v2+, demand-driven):** an "Africa data location" deployment of the data plane in an African region (e.g., AWS `af-south-1` or an African data-centre provider), selected per tenant through the tenant-placement table (Phase 9 §1.5). Trigger: ≥ 3 regulated customers or a large deal requiring it.

## A8. Security operations

- **Incident response plan:**
  - Severity levels, roles (incident commander, comms, scribe), 24h internal triage SLA for security reports.
  - Customer notification within **72h** of confirming a personal-data breach (or faster where contracts require).
  - Regulator notifications per market.
  - Post-incident reviews.
- **Vulnerability management:**
  - SLAs: Critical 7 days, High 30 days, Medium 90 days.
  - Monthly dependency updates.
  - Container base images rebuilt weekly.
- **Responsible disclosure:** `security.txt`, a disclosure page and a safe-harbour statement; bug bounty considered at v2.
- **Vendor/sub-processor management:**
  - Register with DPAs and security reviews: DigitalOcean, CDN/WAF, email provider, Slack, auth provider, FX providers, analytics, error tracking, payments.
  - Annual review.
- **Security training:** onboarding plus annual training for all staff (Cloudboosta academy content can be reused).

## B3. CI/CD pipeline design

**Source control:** GitHub (monorepo: `apps/api`, `apps/worker`, `apps/web`, `packages/*`, `infra/`, `docs/`). Trunk-based development, short-lived branches, protected `main`, required reviews.

```
PR opened ─► CI (GitHub Actions)
  1. Lint + format + type-check (backend, frontend)
  2. Unit tests (+ coverage gate)
  3. Integration tests (Postgres/Valkey/MinIO containers; moto/LocalStack for AWS; tenant-isolation suite)
  4. Contract tests (OpenAPI schema diff; breaking-change check)
  5. Security: SAST, SCA (dependencies), secret scan, IaC scan (Terraform/K8s), container scan
  6. Build images (multi-arch where useful) + SBOM; frontend bundle-size budget check
  7. Fix-template tests (CLI lint, `terraform validate` on recommendation snippets)
  8. Deploy preview environment (optional label)
Merge to main ─► CD
  9. Build, sign (cosign) and push images to registry; tag with commit SHA
 10. Deploy to STAGING (GitOps: Argo CD/Flux syncs Helm values) + DB migrations (expand-only)
 11. Smoke tests + E2E (Playwright) on staging; synthetic AWS connection test
 12. Manual approval (release manager) ─► PRODUCTION progressive rollout
 13. Canary (10% of pods) → health checks / SLO burn → 100%; automatic rollback on failure
 14. Post-deploy smoke tests; release notes; Sentry/OTel release markers
```

- **Database migrations:** expand → migrate → contract pattern; backward-compatible for at least one release; migrations run as a pre-deploy job with a timeout and a tested rollback.
- **Infrastructure:** Terraform (DO + AWS + CDN providers) in `infra/`, with plan on PR, apply on merge with approval, remote state with locking and encryption, and environments as workspaces/directories.
- **Supply chain:** Actions pinned to SHAs; OIDC from GitHub Actions to cloud providers where supported (no long-lived deploy keys; DO tokens scoped and rotated if OIDC is unavailable); signed images verified at admission.
- **Release cadence:** continuous delivery to staging; production deploys daily or on demand during the beta, behind feature flags.

| Item | Approach | Target |
|---|---|---|

| Backup restore tests | Monthly automated restore of a DB snapshot to an isolated environment + data integrity checks | — |

# Part C — Go-to-Market & Pricing Foundations (GTM Strategist)

## C1. Positioning statement

> **For** CTOs, DevOps leads and finance teams at African growth companies running on AWS,
> **who** pay for cloud in dollars but earn in naira, shillings or rand, and lack time or FinOps expertise,
> **Cloudoptics** is a cloud cost platform
> **that** shows what you spend in both currencies, tells you what is safe to cut and how, and verifies the savings.
> **Unlike** global FinOps tools built for US enterprises with FinOps teams and priced in dollars,
> **Cloudoptics** is built for African teams: local-currency pricing and forecasts, risk-scored recommendations with step-by-step fixes, local support, and the Cloudboosta learning community behind it.

**Tagline options (to test):** "See it. Cut it safely. Plan it in your currency." · "Cloud costs, in your currency." · "Safe cloud savings for African builders."

## C2. Messaging pillars

| Pillar | Message | Proof points |
|---|---|---|
| **1. Safe savings** | "Cut cloud costs without breaking production." | Risk score + evidence on every recommendation; rollback steps; 0 incidents in beta; verified savings |
| **2. Your currency** | "Know your cloud bill in naira (or shillings, or rand) — and what next quarter will cost." | Dual currency everywhere; FX scenarios; usage vs FX split in reports |
| **3. Fast and simple** | "Connected in 15 minutes. Results in an hour. No FinOps team needed." | One-click read-only setup; Top 5 actions; plain-language explanations |

| **5. Built in Africa, for Africa** | "Local pricing, local support, local know-how." | Local-currency plans; WAT/EAT/SAST support hours; placement guidance (Cape Town, Lagos/Nairobi Local Zones); Cloudboosta community |

## C5. Pricing strategy hypotheses

**Principles:**
1. **Flat, predictable tiers by monitored AWS spend band**, not a % of savings (buyers distrust it, Phase 2 W4) and not a % of spend.
2. **Priced in local currency**, with purchasing-power-adjusted levels: roughly **30–50% below US equivalents** (H1). Local prices are reviewed quarterly against FX, and existing customers are protected for 12 months from increases.
3. **Value anchor:** fee ≤ 20% of typical realised savings (≥ 5× ROI).
4. **Free entry point** for education and acquisition.

**Hypothesised tiers (USD reference; local price set per country):**

| Tier | Monitored AWS spend / month | Users | Key features | Price (USD-equivalent / month) |
|---|---|---|---|---|
| **Free** | ≤ USD 3,000 | 3 | Dual-currency overview, R1–R3 quick wins, 3 months history, monthly report | Free |
| **Growth** | ≤ USD 25,000 | 10 | All MVP features (R1–R8, workflow, budgets, anomalies, FX scenarios, credits runway, Slack) | **~USD 99–149** |
| **Scale** | ≤ USD 100,000 | 25 | + Jira/Teams, advanced allocation, placement analysis, approved one-click actions (v1), priority support | **~USD 299–449** |
| **Business** | > USD 100,000 | Unlimited | + SSO/SAML, audit export, custom roles, DPA with local clauses, security review support, quarterly expert review | **Custom (from ~USD 900)** |
| **Partner/MSP** | Per managed client | — | Multi-tenant console, white-label, wholesale pricing | Wholesale ~30% off list, or revenue share |

**Options to test:**
- **Annual prepay discount** (~15–20%), which also helps customers lock in a local price.
- **Savings guarantee:** "If verified savings in your first 90 days are less than 3× your fee, we refund the difference." This tests trust and confidence and is attractive to CFOs.
- **Founding customer pricing** for design partners (e.g., 40% off for 12 months).
- **Expert review add-on** (Cloudboosta engineers): fixed price per review.

**Validation:** Phase 4 V4 (Van Westendorp survey + landing page price tests per country) and design-partner conversion (gate G-B).

**Billing operations:**
- Local-currency subscriptions via **African payment providers** (e.g., Paystack and/or Flutterwave; reported coverage includes NGN, GHS, KES, ZAR, EGP and others; confirm recurring-billing support per currency).
- **Stripe** for USD/GBP/EUR customers.
- Invoices with local tax handling (e.g., VAT in Nigeria, Kenya and South Africa; counsel and accountant to confirm digital-services tax obligations).
- Note: some local cards (e.g., Verve in Nigeria) may not support automatic renewal, so support bank transfer and invoice payment as well.
