**Update:** the credentials live in the GitHub environment `github-pages`, so sections 2 and 3 are now automated: run **Actions → Staging setup** from `main` (`.github/workflows/staging-setup.yml`, code in `infra/aws/bootstrap.py` and `infra/digitalocean/provision.py`). ## Before running Staging setup

1. Merge the open PR so `main` has the code and the API image.
2. Add `DIGITALOCEAN_TOKEN` to the same GitHub environment (and as a repository secret for `deploy-staging.yml`).
3. In the WorkOS dashboard (Redirects): add `https://cloudoptics.cloudboosta.com/` as a redirect URI, the sign-in endpoint `https://cloudoptics.cloudboosta.com/sign-in`, and `https://cloudoptics.cloudboosta.com` as an allowed origin (CORS).
4. After a successful run, delete the admin AWS key from the GitHub environment (the app uses the narrowly scoped broker key the workflow creates; re-add the admin key only to run setup again).

## 1. Check the credentials (read-only)

```bash
uv run python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"
```

The keys must be ordinary environment variables. If their values start with `prox`, they were saved as network secrets, which cannot work for AWS request signing.

## 2. AWS: Cloudoptics' own account (ADR-007)

In the account behind the keys (region `eu-west-2` for our resources; CloudFormation for customers stays in `us-east-1`):

1. **Template bucket** `cloudoptics-public-<account-id>`: public read of `cfn/v1/*.yaml` only, versioning, TLS-only policy. Upload `infra/cloudformation/billing-role.yaml` and `resource-role.yaml`. Add a CI step that uploads them on merge when they change.
2. **Broker role** `CloudopticsBroker`: may only `sts:AssumeRole` on `arn:aws:iam::*:role/CloudopticsBillingReadOnly` and `.../CloudopticsResourceReadOnly`. For staging, a dedicated IAM user `cloudoptics-staging-broker` whose only permission is assuming `CloudopticsBroker` (access key stored as App Platform secrets `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` on `api` and `worker`). Replace with IAM Roles Anywhere when we move to DOKS (spike CC-1).
3. Update `infra/digitalocean/app.yaml` envs: `CLOUDOPTICS_CLOUDOPTICS_PRINCIPAL_ARN` (the broker role ARN), `CLOUDOPTICS_CFN_BILLING_TEMPLATE_URL`, `CLOUDOPTICS_CFN_RESOURCE_TEMPLATE_URL`, `CLOUDOPTICS_CFN_QUICK_CREATE_ENABLED=true`. `SessionFactory` must assume the broker role first, then the customer role (role chaining keeps the customer trust policy pointing at one stable ARN).
4. Test end to end against a real account with `infra/cloudformation/billing-role.yaml`.

Never commit keys. Rotate the admin key you were given once the broker user exists.

3. API: set `CLOUDOPTICS_OIDC_ISSUER`, `CLOUDOPTICS_OIDC_AUDIENCE` (client ID) and `CLOUDOPTICS_OIDC_JWKS_URL` (`https://api.workos.com/sso/jwks/<client_id>`) in `app.yaml`; check the issuer value against a real token before relying on it. Each successful scan queues `analysis.run`, which applies rules R1 (unattached volumes, old orphaned snapshots), R2 (idle Elastic IPs, idle load balancers) and R3 (gp2 to gp3), scores them (PRD FR-REC-03/04), and stores them in `recommendation` keyed by rule and resource, with CLI fix and rollback commands. `GET /v1/tenants/{t}/recommendations` (and `/summary`, `/{id}`) serve them. Savings use the tenant's own CUR rate where it has one, else list prices from `price_catalog` (seeded with us-east-1 prices as the `*` fallback). Follow-up: a Price List refresh job needs `pricing:GetProducts` on the Cloudoptics broker role (`infra/aws/bootstrap.py`).
- Sprint 3, connection alerts and audit log (FR-CON-09, FR-NOT-02, FR-SEC-05): every 6 hours the worker re-checks each connection that has been validated (`connection.check`, validation only). When a connection that was working gets worse (healthy to degraded or failed, degraded to failed) its admins get one email per connection, state and day through Postmark (`notification` table). Email needs `POSTMARK_API` (a Postmark Server API token) in the `github-pages` environment, then a run of **Staging setup** to copy it to App Platform as `CLOUDOPTICS_POSTMARK_SERVER_TOKEN`; without it emails are logged, not sent. The sender defaults to `CloudOptics <alerts@cloudboosta.com>`: verify that address or the `cloudboosta.com` domain in Postmark, or set `POSTMARK_FROM` to a verified sender. A new Postmark account can only email its own domain until Postmark approves it. Admins see the audit log under Settings (`GET /v1/tenants/{t}/audit-log`, paged, with a hash-chain integrity check).
- Single onboarding stack (23 Oct 2026): `infra/cloudformation/cloudoptics-access.yaml` (version 2.0.0) replaces the billing, resource and StackSet stacks for new connections. Onboarding has no account form: `POST /v1/tenants/{t}/connections/intents` makes a one-click link, and the stack's setup step (`infra/cloudformation/setup/access_setup.py`, embedded with `setup/embed.py`) calls `POST /v1/cfn/callback` with the account, which creates the connection and starts the access check. The callback is not signed in; it proves itself with the connection's External ID. The setup step removes the older Cloudoptics stacks on create (StackSet stack, then resource, then billing), reuses the kept `cloudoptics-cur-<account>` bucket, and in an Organization's management account manages the `cloudoptics-resource-access` StackSet itself (create, update, delete). Connections on the older stacks see "Move to the single stack" (same connection and External ID, so history stays). `cloud_connection.stack_version` records the version each stack reports; a newer `ACCESS_TEMPLATE_VERSION` shows "Update Cloudoptics access". AWS has no documented deep link to a stack's update page with a new template, so the update panel links the stack and gives the template address to paste. Staging setup uploads the new template.
- Template 2.0.2 (24 Oct 2026), checked against the AWS docs (Service Authorization Reference, StackSets and Organizations guides, Data Exports guide). The setup role may now create the StackSets service-linked role (`AWSServiceRoleForCloudFormationStackSetsOrgAdmin`): it was refused under an `iam:AWSServiceName` condition, which CloudFormation's ActivateOrganizationsAccess request does not carry, so the grant is now scoped by the role's path. `cloudformation:CreateStackSet` supports no resource-level permissions and now has `Resource: "*"` (scoped to the stack set's ARN it was always refused). Stack-set target and resource-type ARNs carry an account field. Removing the older stacks also gets `ec2:DescribeNetworkInterfaces`, `iam:TagRole`/`UntagRole` and `cloudformation:UntagResource`. - Invites and members (24 Oct 2026, ADM-3, PRD US-8.1): admins invite an email with a role under Settings → Members (`POST/GET /v1/tenants/{t}/invites`, `DELETE .../invites/{id}`), change roles and remove members (`PATCH/DELETE .../members/{userId}`; a workspace always keeps one admin). There is no link to click: the next time someone with that email signs in (`GET /v1/me`), they join, but only if WorkOS reports the email as verified. Invites expire after 7 days, and inviting again replaces the open one. Each step is in the audit log (`invite.created`, `invite.revoked`, `member.joined`, `member.role_changed`, `member.removed`). The invite email goes through Postmark when it is configured; otherwise the admin is told to let the person know. Table `invite` (migration 0015) is tenant-isolated, and a user may also read the invites addressed to their own email.
- Scan results on Connections (24 Oct 2026): `GET /v1/tenants/{t}/resources/summary` now returns `scans`, each connection's latest inventory scan from `sync_run`: status, time, resources, regions, accounts with access, and `errors` ("<account> <region>: <AWS error code>"). A scan that crashes is now recorded as `failed` instead of disappearing. Admins always get **Scan now** on the resource access panel (it used to appear only while an account lacked access), and the panel shows the last scan's result and what could not be read.
- Prices for every region (26 Oct 2026): the first real recommendations (test volume and Elastic IP in eu-west-2) priced gp2 at the us-east-1 $0.10 instead of London's $0.116, because only us-east-1 prices were seeded and the account's own London gp3 rate, divided by the us-east-1 price, was capped at 1 as a "discount". `python -m cloudoptics.analysis.price_list` now reads the public AWS Price List (on-demand CSV offer files for AmazonEC2, AWSELB, AmazonVPC and AmazonRDS; no credentials) for all 36 AWS Regions and writes `apps/api/migrations/data/price_list.json` (EBS, public IPv4, load balancers, the `large` price of every EC2 family and of RDS PostgreSQL/MySQL Single-AZ families). Migration 0016 loads it (source `price_list`) and makes `*` a copy of us-east-1. To refresh prices, run the module again and add a migration that loads the file. A ratio measured against fallback prices is no longer capped.
- Immediate flags (26 Oct 2026, the user's decision): unattached EBS volumes, unattached Elastic IPs and idle load balancers are recommended from the first scan that finds them, with Low confidence, rising to Medium (volumes 7 days, IPs and load balancers 3 days) and High (32 / 7 / 7 days). A volume detached under 7 days ago and a load balancer under 7 days old add 10 risk points. PRD FR-ANA-01/02/02b updated.
- Scan progress (26 Oct 2026): a scan is recorded in `sync_run` as `running` from the moment Scan now queues it (the worker takes that row over) or the worker starts it, and every 2 seconds the worker writes `scope.progress` (`regionsDone`, `regionsTotal`; accounts not reached yet count at the average seen so far). `GET /resources/summary` returns it as `status: "running"` with `progress`, and the Connections page polls every 2 seconds while one runs, so the progress bar survives leaving the page, reloading, and shows for every admin. A `running` row older than 30 minutes (worker restarted) reads as `failed` with `interrupted`, and the next scan marks it so.

- Budgets and alerts (27 Oct 2026, PRD US-6.1/6.2, WBS API-6/FE-9): `/v1/tenants/{t}/budgets` (list and read for viewers; create, edit, pause and delete for members and admins; audited as `budget.*`) and the Budgets page. A budget is monthly, for the whole workspace or chosen accounts, in USD or the workspace currency; a local-currency budget is converted with the latest rate and shows "No exchange rate" (no alerts) until staff set one. Spend is this month's bills (CUR), amortised after credits, with the Overview's run-rate forecast. Thresholds (default 50/80/100% of spend and 100% of forecast) email the chosen members and addresses once a month each (`notification` key `budget:<id>:<kind>:<percent>:<YYYY-MM>`; a failed send is tried again). `budgets.evaluate` runs after each bill load and hourly (`budgets.poll`, minute 23) on the existing `notifications` queue. Not yet: tag-scoped budgets (cost aggregates keep only a tag hash), Slack recipients, and Cost Explorer's provisional figures at the start of a month (budgets wait for the first bill).
- Anomaly detection (27 Oct 2026, PRD US-6.3, FR-ANA-08, WBS AN-11/FE-6): module `apps/api/src/cloudoptics/anomalies` (tables `anomaly` and `alert_setting`, migration 0019). Per (account, service) and day of bills (usage and purchases, amortised; credits, refunds and tax left out), the expected cost is the median of the same weekday over the four weeks before and MAD the median absolute deviation of those four days; a day is an anomaly when it is above expected + max(3 x MAD, 30%) and at least USD 50 above expected. Both thresholds, the minimum's currency (USD or the workspace currency; without a rate the USD 50 default applies) and extra alert addresses are set by admins at `GET/PUT /v1/tenants/{t}/alert-settings` (audited `alert_settings.updated`). Each run re-checks the last 7 days of bills (a day's bill fills in for a while); a day needs four weeks of bills before it, so a new workspace finds anomalies from its 29th day of data. New open anomalies of a run go to the workspace's admins and members (plus the extra addresses) as one email, once each (`notification` key `anomaly:<id>`, a failed send is retried). `/v1/tenants/{t}/anomalies` lists them (viewer+, `?status=`), `GET /{id}` adds the daily series with the expected level and alert level, `PATCH /{id}` sets open / investigating / expected / resolved with a note (member+, audited `anomaly.status_changed`). Marking one expected stores the same scope's anomalies of the next 7 days as expected (`suppressed_by`), without an alert. `anomalies.detect` runs after each bill load and hourly (`anomalies.poll`, minute 37) on the `analysis` queue. The Anomalies page replaces "coming soon" (list with status tabs, chart, top usage types, triage, thresholds). Not yet: Slack, resource-level contributors (cost aggregates stop at usage type and region), anomaly markers on the Overview chart, a deep link into the Cost Explorer pre-filtered, and "expected" tuning beyond the 7-day suppression.
